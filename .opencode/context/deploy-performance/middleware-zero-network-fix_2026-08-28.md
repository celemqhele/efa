# Middleware zero-network fix + NavShell Suspense streaming

**Date:** 2026-08-28
**Category:** deploy-performance (follow-up to `middleware-timeout_2026-08-28.md`)

## Problem (recurrence)

Narrowing the middleware matcher (`a715818`) reduced *where* middleware ran but
did **not** fix the 504. A fresh `MIDDLEWARE_INVOCATION_TIMEOUT` was observed at
2026-08-27T23:09Z (~5 min after the latest production deploy
`dpl_9Tk18i8QzRzSpZsZ9io8bUzZNNMP`), and the user again reported "first page
works, navigating to other pages gets stuck".

## Root cause

Blocking **Supabase auth network calls** sat in the request hot path of every
navigation:

1. `middleware.ts` called `await supabase.auth.getUser()` — a blocking
   round-trip to Supabase's auth server — on every `/profile`, `/notifications`,
   `/admin`, `/login`, `/register` request. Supabase auth was healthy (~350 ms
   from the dev machine), so the hang was the Vercel edge-region → supabase.co
   leg stalling intermittently past Vercel's 25 s initial-response deadline →
   `MIDDLEWARE_INVOCATION_TIMEOUT`.

2. `components/ui/PageWrapper.tsx` (used by the `(public)`, `(protected)`, and
   `(admin)` layouts) ALSO awaited `supabase.auth.getUser()` on every page
   render (plus profile + unread-count queries for logged-in users) **before**
   streaming its shell. Any Supabase auth slowness stalled navigation to ANY
   page, including public ones.

The earlier matcher-only fix was necessary but not sufficient — the dependency
on a network call inside middleware remained.

## Fix

### 1. `middleware.ts` — zero network, local cookie check only
- Removed `createServerClient`/`getUser()` entirely.
- Protected/admin routes now redirect to `/login?redirect=...` only when no
  Supabase session cookie is present (`sb-*-auth-token`), purely local.
- `/login` & `/register` redirect to `/` when the cookie is present.
- `matcher` config unchanged.
- **Security unchanged:** every protected page/layout already re-validates
  server-side with `getUser()` + `redirect()` — `app/(admin)/layout.tsx`,
  `app/(protected)/notifications/page.tsx`, the `profile` pages. Cookie refresh
  is still handled by `createClient` during page renders.
- Middleware bundle dropped 63.5 kB → 34.2 kB. `MIDDLEWARE_INVOCATION_TIMEOUT`
  is now impossible by construction.

### 2. PageWrapper → Suspense streaming
- New async server component `components/ui/NavShell.tsx` holds the auth
  (`getUser()`) + profile + unread-count logic and renders `Nav` + `BottomTabBar`.
- `components/ui/PageWrapper.tsx` renders `<Suspense fallback={<NavSkeleton/>}>
  <NavShell/></Suspense>` so the page shell streams immediately; the nav fills
  in when Supabase responds. Pages no longer block first paint on the network.

## Verification
- `npm run lint` — passes (only pre-existing unrelated warnings).
- `npm run build` — succeeds; middleware 34.2 kB.
- `.next/server/middleware-manifest.json` — matchers still resolve to only
  `/profile`, `/notifications`, `/admin`, `/login`, `/register`.
- `public/sw.js` regenerated by the build (chunk-hash/precache updates only).
- Live post-deploy test: public + protected nav sub-second, no middleware timeout.

## Confirmed working (production)

Deployed as `dpl_3zYEDsWPHaQYW5jmEBeEuRyAWgZS` (production alias
`efa-fxyk.vercel.app`, target production). Live checks on 2026-08-28 after deploy:

- `/` → HTTP 200 in ~3.6 s (first cold hit; Suspense shell streams immediately)
- `/standings` → HTTP 200 in ~0.9 s
- `/profile`, `/notifications`, `/admin` → HTTP 307 to `/login` in ~0.4 s each
  (middleware now local-only — no Supabase round-trip)

User confirmed: **"it works"** — navigation no longer hangs, no further
`MIDDLEWARE_INVOCATION_TIMEOUT` reports from the user after this fix.
